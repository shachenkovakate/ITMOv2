## 1. Что увидит пользователь

Один экран: поле «Diff одного PR», счётчик символов, «Проверить diff» и
«Очистить». После анализа — краткое описание, раздел «Возможные риски» (до трёх) с указанием
файла/строки/доказательства и список того, что стоит проверить.
Без истории, аккаунтов, загрузки файлов и действий с GitHub.

Состояния: idle → loading → success либо error. При запуске предыдущий
результат очищается, ввод и обе кнопки блокируются. При ошибке ввод сохраняется,
блокировка снимается; повтор возможен только вручную. При изменении текста
предыдущий результат скрывается. Очистка возвращает пустой idle и фокус в поле.
Текст diff и ответа выводится буквально, без выполнения HTML/скриптов.

На форме есть доступные подписи и видимый фокус; состояния объявляются
assistive technology. Контрольный экран — от 360 CSS px без горизонтальной
прокрутки всей страницы. Демонстрационный результат явно помечается «ДЕМО».

## 2. Вход и запрос

`POST /api/reviews`, `Content-Type: application/json`:

```json
{"diff":"...текст unified diff..."}
```

Только поле diff строкового типа. 1–20000 Unicode code points исходной строки,
пробельная строка недопустима. Счётчик одинаков на клиенте и сервере: до trim,
маскирования и нормализации переносов. UI передаёт ровно строку из поля.
LF и CRLF допустимы; CRLF считается двумя code points в полученном входе.
Сам браузер может нормализовать вставленные переносы в textarea, поэтому
UI считает фактическое значение поля, а не размер исходного файла на диске.

UI проверяет непустоту и длину; сервер независимо проверяет форму и структуру.
Сервер принимает обычный текстовый unified diff: пара ---/+++, hunk @@,
хотя бы одно добавление или удаление. Поддерживаются несколько файлов и
/dev/null для создания/удаления. Пути — только метки, файлы по ним не читаются.
Для учебных фрагментов число показанных строк может отличаться от счётчиков
hunk; начальные номера сохраняются, отсутствующие строки не восстанавливаются.
Binary, combined merge, rename-only и Git-экранированные пути вне этого scope.

## 3. Успех и доказательства

HTTP 200:

```json
{
  "request_id": "f2a7a4a0-8e22-4b26-a616-607993d0fb17",
  "mode": "live",
  "summary": "Изменена обработка запроса.",
  "risks": [
    {"file":"app/api.py","line":8,"evidence":"+    return payload[\"diff\"]","risk":"Обращение по ключу без проверки его наличия."}
  ],
  "checks": ["Передать пустой объект и проверить контролируемый отказ."]
}
```

Пример иллюстрирует форму, а не утверждает номер строки реального входа.
Модель выдаёт только summary/risks/checks; request_id и mode добавляет сервер.

- summary: непустая после trim строка, до 1500 code points.
- risks: 0–3 объекта ровно с file, line, evidence, risk.
- file: непустой нормализованный путь, встречающийся в diff.
- line: целое > 0, не boolean; новая версия для добавлений/контекста,
  старая версия для удалений.
- evidence: точная строка очищенного diff вместе с префиксом +, - или пробелом;
  длина не больше 20000. Она обязана совпасть с указанными файлом и координатой.
- risk: непустая строка до 1000 символов. В ней можно сослаться на известное
  правило Context Pack и объяснить его применимость к указанной строке.
  Риски без координат и без цитаты в первой версии не выдаются.
- checks: 1–10 непустых строк, каждая до 500 символов.
- mode: live или demo. Demo — явная воспроизводимая подмена; скрытого fallback нет.

Некорректный результат отклоняется целиком, без усечения до трёх рисков и
достраивания полей. Сервер отклоняет лишние поля модели. UI допускает
добавочные служебные поля envelope, но проверяет обязательную форму и границы.
Наличие цитаты подтверждается автоматически; истинность вывода проверяет человек.
Нулевой risks отображается с пояснением, что это не гарантия отсутствия ошибок.

## 4. Ошибки и ожидание

```json
{
  "request_id": "f2a7a4a0-8e22-4b26-a616-607993d0fb17",
  "error": {"code":"DIFF_TOO_LARGE","message":"Diff превышает лимит 20 000 символов."}
}
```

| HTTP | code | Действие пользователя |
|---|---|---|
| 415 | UNSUPPORTED_MEDIA_TYPE | Передать JSON; ошибка интеграции, не обычного UI |
| 400 | INVALID_JSON | Исправить JSON; ошибка интеграции |
| 422 | INVALID_REQUEST | Исправить форму, тип, пустой ввод или лишние поля |
| 413 | DIFF_TOO_LARGE | Сократить diff до лимита |
| 422 | INVALID_DIFF | Вставить текстовый unified diff |
| 422 | UNSUPPORTED_DIFF | Использовать поддерживаемый текстовый diff |
| 503 | MODEL_NOT_CONFIGURED | Настроить модель на сервере |
| 504 | MODEL_TIMEOUT | Повторить вручную позже |
| 502 | MODEL_UNAVAILABLE | Повторить вручную позже |
| 502 | INVALID_MODEL_OUTPUT | Повторить вручную; частичное ревью не показывается |
| 500 | INTERNAL_ERROR | Сохранить request_id для диагностики |

message — безопасная русская строка, не исключение провайдера. UI определяет
сообщение по code, неизвестные коды получают общий безопасный текст.
retryable не передаётся: фиксированная таблица UI задаёт действие пользователя.
Локальная ошибка формы и ошибка сети не обязаны иметь request_id.

Порядок серверной проверки: content type → JSON → форма/тип → длина → пустота →
структура diff → настройки модели → анализ. При отказе до анализа LLM не вызывается.
Один запрос — максимум один вызов модели, бюджет 10 секунд. UI прекращает
ожидание через 15 секунд; поздний ответ завершённой попытки игнорируется.
Автоматических повторов нет. На сервере отмена обработки должна отменять ожидание
провайдера; это не гарантия отмены уже начатых вычислений на стороне провайдера.

## 5. Приватность и режимы

Ключ модели не передаётся в браузер и не сохраняется в репозитории. Маскируются
описанные в предложении логики присваивания token/password/passwd/secret/api_key,
Bearer, префиксы ghp_/github_pat_/sk- и PEM private key. Перед планированием этот
конечный список переносится в обе согласованные спецификации без расширений.
Количество строк и координаты сохраняются. Ответ повторно маскируется; итоговая
структура и совпадение evidence проверяются после маскирования.
Неизвестные форматы секретов этим механизмом не гарантируются.

В журнале только request_id, duration_ms, status. Хранения истории нет.
Режим выбирает конфигурация сервера, не запрос клиента. В demo действует тот же
контракт и валидаторы; UI сообщает о подмене. Для live используется отдельно
настроенный провайдер. Его качество не доказывается тестами с подменой.

## 6. Приёмка после согласования

1. Вставить учебный diff, получить и прочитать результат через UI.
2. Проверить 20000/20001 символ и пустой ввод: ошибка понятна, ввод сохранён,
   превышение и пустота не вызывают модель.
3. Проверить сбой/таймаут и неверное evidence: нет частичного успеха,
   интерфейс выходит из loading и допускает новый ручной запуск.
4. Проверить совпадение file/line/evidence, 0 и 3 риска, отказ при 4 рисках.
5. Проверить literal rendering, клавиатуру, очистку и отсутствие старого результата.
6. Проверить маскирование синтетических секретов и состав журнала.

На момент согласования прикладной код отсутствовал. Проверки и демо выполняются на этапе реализации.
