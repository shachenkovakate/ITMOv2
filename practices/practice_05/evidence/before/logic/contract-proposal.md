# Предложение контракта команды логики

**Status**: Draft — awaiting human agreement  
**Дата**: 2026-10-27  
**Основание**: независимый [spec.md](spec.md), Context Pack. Это предложение, не общий контракт и не решение человека. API ниже пока не реализован.

## Граница операции

Предлагается сохранить знакомый исходному сценарию `POST /api/reviews`. JSON в UTF-8, ответ `application/json`. Синхронный запрос, без streaming, job polling, сохранения истории и автоматических повторов. Запрос:

```json
{"diff":"diff --git a/example.py b/example.py\n--- a/example.py\n+++ b/example.py\n@@ -1 +1 @@\n-old()\n+new()\n"}
```

Только одно обязательное поле `diff` строкового типа; неизвестные поля отклоняются. `null`, массив, число, отсутствие diff и пустая/пробельная строка недопустимы. После проверки типа первым проверяется лимит: более 20 000 Unicode code points исходной строки → 413. Иначе проверяется непустота и структура. Размер считается до замены CRLF на LF, trim и маскирования, поэтому клиент должен считать ту же исходную строку. Клиентская проверка дополняет серверную.

Предлагается поддерживать текстовые фрагменты unified diff: пара `---`/`+++`, один или несколько `@@ -old[,count] +new[,count] @@`, хотя бы одна строка изменения. Разрешены несколько файлов, LF/CRLF, создание и удаление с `/dev/null`; заголовок `diff --git` необязателен. Префиксы `a/`, `b/` удаляются из путей; timestamp после табуляции в заголовке не часть пути. Путь назначения используется кроме удаления файла. Пути с Git-кавычками/escape-последовательностями, combined merge, binary и rename-only отклоняются как `UNSUPPORTED_DIFF`. Строка `\ No newline at end of file` допускается и не увеличивает координаты. Отсутствие файлов/hunks/изменений либо непонятные строки внутри hunks → `INVALID_DIFF`.

Declared counts в hunk не сверяются с числом строк: обязательный TRAINING_PR.diff является сокращённым фрагментом. Начальные координаты используются буквально; строки между hunks не восстанавливаются. Все пути — метки для ответа, чтение файлов по ним запрещено.

## Успешный ответ

HTTP 200:

```json
{
  "request_id": "f2a7a4a0-8e22-4b26-a616-607993d0fb17",
  "mode": "live",
  "summary": "Изменён способ обработки результата.",
  "risks": [
    {
      "file": "example.py",
      "line": 1,
      "evidence": "+new()",
      "risk": "Новая функция вызывается без показанной обработки ошибки; проверьте ожидаемое поведение при исключении."
    }
  ],
  "checks": ["Подставить функцию, выбрасывающую исключение, и проверить ожидаемый результат вызова."]
}
```

Пример показывает только форму, не эталонный вывод о коде. Неизвестные поля в результате модели отклоняются. Служебные `request_id` и `mode` добавляет сервис; модель возвращает только summary, risks, checks.

| Поле | Предлагаемый тип и ограничения |
| --- | --- |
| request_id | Непустой UUID; новый для каждой попытки, в том числе ошибки; не берётся из diff или ответа модели |
| mode | `live` или `demo`; фактический источник успешного результата, определён конфигурацией сервиса |
| summary | Строка, 1–1500 Unicode code points после trim |
| risks | Массив из 0–3 элементов, каждый ровно с file, line, evidence, risk |
| risks[].file | Строка с точным нормализованным путём из diff либо `null` для риска только по правилу без координат |
| risks[].line | Положительное целое (не boolean) либо `null` одновременно с file |
| risks[].evidence | Непустая строка длиной не более 20 000 символов; точная строка отредактированного diff вместе с префиксом, либо `RULE:<ID>` |
| risks[].risk | Строка, 1–1000 символов после trim |
| checks | Массив из 1–10 непустых строк по 1–500 символов после trim; описание действия и ожидаемого наблюдения |

Отсутствие поля, неверный тип, превышение ограничения, code fence вместо JSON, дополнительный текст или четыре риска → `INVALID_MODEL_OUTPUT`; ничего не обрезается автоматически. Система маскирует поддерживаемые секреты в строковых полях ответа и проверяет окончательную структуру до выдачи.

## Значение evidence и line

1. **Цитата diff**: evidence точно равно одной строке уже отредактированного diff, включая ведущие `+`, `-` или пробел. `file` совпадает с путём этой строки. Для `+` и пробела `line` — номер новой версии, для `-` — номер старой. Заголовки файла/hunk не считаются цитатами кода. Идентичная цитата в другом файле или на другой строке не подтверждает риск.
2. **Правило**: evidence равно `RULE:SEC-1`, `RULE:API-1`, `RULE:REL-1`, `RULE:OUT-1`, `RULE:SCOPE-1`, `RULE:QA-1` либо `RULE:OBS-1`. При `file: null, line: null` это риск только по правилу; если координаты заданы, они должны существовать среди строк соответствующего файла (в старой либо новой версии). Формулировка risk объясняет, почему правило относится к показанному изменению. Неизвестные ID запрещены.
3. **Ограничение проверки**: наличие строки/правила проверяется автоматически; корректность вывода о последствиях не гарантируется. Использование правила не даёт модели права утверждать устройство непоказанного кода.

Пример удалённой строки: `{"file":"example.py","line":1,"evidence":"-old()","risk":"..."}`. Пример риска только по контексту: `{"file":null,"line":null,"evidence":"RULE:SCOPE-1","risk":"Проверка остаётся рекомендацией; решение по PR принимает ревьюер."}`. Последний пример описывает форму, а не обязательный риск в каждом ответе.

## Контролируемые ошибки

Все ошибки имеют единую форму и не содержат частичного ревью:

```json
{
  "request_id": "f2a7a4a0-8e22-4b26-a616-607993d0fb17",
  "error": {
    "code": "DIFF_TOO_LARGE",
    "message": "Diff превышает лимит 20 000 символов.",
    "retryable": false
  }
}
```

`message` — безопасная русская строка, не текст исключения провайдера. UI опирается на code, не сравнивает message. `retryable` означает, что можно повторить тот же ввод после временной ошибки; любой запуск только вручную. Для исправимого ввода false не запрещает отправить изменённый diff.

| HTTP | code | Условие | retryable | Вызов модели |
| --- | --- | --- | --- | --- |
| 415 | UNSUPPORTED_MEDIA_TYPE | Тело не объявлено JSON | false | Нет |
| 400 | INVALID_JSON | Синтаксически неверный JSON | false | Нет |
| 422 | INVALID_REQUEST | Не объект, неверные/лишние поля, пустой diff | false | Нет |
| 413 | DIFF_TOO_LARGE | Строка длиннее 20 000 символов | false | Нет |
| 422 | INVALID_DIFF | Не распознана структура текстового diff | false | Нет |
| 422 | UNSUPPORTED_DIFF | Узнан неподдерживаемый вид diff или пути | false | Нет |
| 503 | MODEL_NOT_CONFIGURED | Для live не заданы необходимые настройки модели | false | Нет |
| 504 | MODEL_TIMEOUT | Вызов модели не завершён за 10 секунд | true | Один |
| 502 | MODEL_UNAVAILABLE | Ошибка транспорта/провайдера, включая rate limit | true | Один |
| 502 | INVALID_MODEL_OUTPUT | Форма или evidence ответа не проходят проверку | true | Один |
| 500 | INTERNAL_ERROR | Непредвиденная ошибка приложения | false | Не более одного |

Последовательность: content type → разбор JSON → форма/тип → длина → пустота → структура diff → конфигурация → анализ. Это делает исход для нескольких одновременных проблем предсказуемым. Проверяемый ответ содержит request_id даже при ошибке до обращения к модели.

## Редактирование секретов и приватность

Предложение минимально проверяемого покрытия SEC-1, не гарантия обнаружения любых секретов:

- Значения в одной строке после `=` или `:` у ключей `token`, `password`, `passwd`, `secret`, `api_key` без учёта регистра; ключ может быть обёрнут в одинарные/двойные кавычки, пробелы вокруг разделителя разрешены. Для строкового значения в кавычках заменяется содержимое до соответствующей закрывающей кавычки; для значения без кавычек — последовательность до пробела, запятой, `;` или конца строки. Пустое значение остаётся пустым. Экранированные кавычки внутри такого значения должны учитываться.
- Значение credentials после слова `Bearer` и пробела, до пробела/кавычки/конца строки.
- Отдельные токены с префиксами `ghp_`, `github_pat_`, `sk-` и последующими не менее 8 символами из букв, цифр, `_`, `-`.
- Блоки от `-----BEGIN PRIVATE KEY-----`, `-----BEGIN RSA PRIVATE KEY-----`, `-----BEGIN EC PRIVATE KEY-----`, `-----BEGIN OPENSSH PRIVATE KEY-----` до соответствующего END. Каждый непустой payload строки заменяется отдельно, сохраняя количество строк и префиксы diff; если END отсутствует — маскируются все оставшиеся payload строки diff. Структурные заголовки diff остаются для навигации, содержимое ключа не отправляется.

Значения заменяются на `[REDACTED]`; совпадения ищутся и в добавлениях, и в удалениях, и в контексте. Одинаковые правила применяются к ответу модели. Маскирование не охватывает произвольные обфускации, неизвестные форматы и секреты, неотличимые от обычного текста. Перед реальным анализом используются учебные данные, не реальные ключи.

Приложение хранит исходный и очищенный ввод только в памяти обработки попытки, без истории и файлов дампов. Ключ провайдера задаётся вне браузера и репозитория. Журнал приложения содержит только request_id, duration_ms и status; body, prompt, headers и response не логируются. Политика хранения у выбранного внешнего провайдера не задана и не должна выдумываться.

## Режимы и вопросы согласования

Предложение: `live` использует внешний LLM, `demo` — явно помеченную воспроизводимую подмену, выбранную настройкой сервиса. Вход не может переключить режим. В demo сохраняются те же валидация, маскирование, структура ответа и проверка evidence. Нельзя делать скрытый fallback live → demo. Конкретный SDK, язык и framework этим draft не задаются.

Для человеческого согласования предложены, но пока не приняты: способ подсчёта символов; поддерживаемое подмножество diff; координаты удалений; null-координаты и синтаксис правила evidence; HTTP-статусы и error envelope; служебные поля mode/request_id; отказ всего результата при ошибке модели; live/demo и отсутствие авторизации в локальном scope. Провайдер/модель и доступность ключа остаются реальной неопределённостью перед живым запуском. Остальные решения имеют описанный разумный default и не требуют остановки независимого проектирования.

### Конкретные варианты для общего согласования

| Вопрос | Предложение логики | Другой разумный вариант и последствие |
| --- | --- | --- |
| Принимать ли сокращённые hunks исходного учебного diff? | Да: доверять начальным координатам, не требовать совпадения declared counts; учебный вход работает без исправлений | Нет: строго сверять counts; тогда исходный TRAINING_PR.diff будет отклонён и для демо потребуется отдельный исправленный fixture |
| Как представлять доказательство? | Точная строка с префиксом либо `RULE:<ID>`; для контекстного риска допустимы null-координаты | Требовать строку diff для каждого риска; проще навигация, но теряется предусмотренный QA-1 случай доказательства только правилом |
| Как показывать демонстрационный анализ? | Отдельный явно обозначенный mode `demo`, реальный анализ — `live` | Только live; проверка с подменой остаётся тестовой, но интерактивная демонстрация требует доступного провайдера и ключа |

Это вопросы родителю для сопоставления и человека для решения; ответы пока не получены.
