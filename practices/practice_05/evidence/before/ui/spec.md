# Feature Specification: Браузерное ревью diff — UI

**Feature Branch**: `practice_05`

**Created**: 2026-10-27

**Status**: Draft — awaiting human agreement

**Input**: Независимая спецификация команды UI для ДЗ 5 «Две команды — одна фича»: ревьюер вставляет unified diff одного PR и получает краткое описание, до трёх доказуемых рисков и проверки. Источники: [Context Pack](../../../inputs/context.md), [сценарии](../../../inputs/product_management.md), [учебный diff](../../../inputs/TRAINING_PR.diff), [constitution](../../.specify/memory/constitution.md).

Это первоначальное предложение команды UI. Спецификация команды логики не использовалась. Все новые решения UX и границы обмена данными ниже ещё не согласованы человеком. Отдельный [проект контракта UI](contract-proposal.md) предназначен для сопоставления; он не является общим утверждённым контрактом. Код до согласования не создаётся.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Получить проверяемую рекомендацию (Priority: P1)

Ревьюер вставляет diff, запускает анализ и читает описание изменения, доказательства рисков и воспроизводимые проверки, чтобы самостоятельно решить, что проверить в PR.

**Why this priority**: Это основной результат продукта и минимальный законченный пользовательский путь.

**Independent Test**: На отдельной странице вставить учебный diff и получить явно обозначенный воспроизводимый ответ модели. Это проверяет представление рекомендации, но не доказывает качество реального LLM.

**Acceptance Scenarios**:

1. **Given** открыта пустая страница, **When** ревьюер вставляет учебный diff допустимой длины, **Then** видит число символов, лимит и кнопку «Проверить diff».
2. **Given** допустимый diff, **When** запущен анализ, **Then** виден текст «Анализируем diff…», ввод и повторная отправка недоступны; результата прошлого запуска нет.
3. **Given** корректный ответ с тремя рисками, **When** он показан, **Then** присутствуют «Краткое описание», «Риски (3)» и «Что проверить»; у каждого риска видны путь, строка, доказательство и описание риска; порядок элементов сохранён.
4. **Given** корректный ответ без рисков, **When** он показан, **Then** видны summary, checks и текст «Подтверждённых рисков не найдено. Это не гарантирует отсутствие ошибок».
5. **Given** ответ содержит текст, похожий на разметку или команду, **When** он показан, **Then** текст читается буквально, не выполняется и не создаёт скрытых действий.

---

### User Story 2 - Исправить вход или повторить анализ (Priority: P2)

Ревьюер получает понятную причину отказа, сохраняет вставленный текст и может исправить вход или повторить попытку.

**Why this priority**: Ошибки внешней модели и ограничение размера заданы источником; без восстановления основной сценарий обрывается.

**Independent Test**: Использовать пустой ввод, границы размера и управляемые ответы ошибок. Успешный ответ модели для этой проверки не требуется.

**Acceptance Scenarios**:

1. **Given** пустой или пробельный ввод, **When** пользователь пытается запустить анализ, **Then** видит «Вставьте diff одного PR», фокус переходит в поле и анализ не начинается.
2. **Given** непустой diff на 20 000 символов, **When** пользователь запускает анализ, **Then** ограничение размера не мешает отправке; для 20 001 символа показана ошибка размера и анализ не начинается.
3. **Given** служба отклонила запрос по размеру вопреки предварительной проверке, **When** получен отказ, **Then** UI показывает лимит 20 000 и сохраняет ввод; служба остаётся окончательным источником решения о допустимости.
4. **Given** произошла ошибка модели, её таймаут или потеря связи, **When** UI получает отказ либо истекает его ожидание, **Then** ожидание завершается контролируемой ошибкой, ввод сохранён, можно вручную повторить запрос; автоматического повтора нет.
5. **Given** ответ содержит более трёх рисков, риск без доказательства или неверную структуру, **When** UI обрабатывает его, **Then** результат целиком скрыт и показано «Получен некорректный результат. Повторите попытку»; UI не обрезает риски и не дополняет доказательства.

---

### User Story 3 - Управлять просмотром без мыши (Priority: P3)

Ревьюер проходит форму и читает результат с клавиатуры и программой чтения с экрана, затем очищает экран для следующего PR.

**Why this priority**: Доступность нужна всем состояниям; очистка явно завершает работу с текущим diff.

**Independent Test**: Пройти форму клавиатурой с управляемым завершением анализа, проверить объявления состояния и очистку. Это самостоятельная проверка доступности оболочки.

**Acceptance Scenarios**:

1. **Given** открыта форма, **When** пользователь перемещается Tab и активирует кнопки клавиатурой, **Then** все доступные действия достижимы, порядок соответствует чтению, фокус виден и не заперт.
2. **Given** активна программа чтения с экрана, **When** меняется состояние анализа, **Then** доступны название поля, его ошибка и сообщение о начале, успехе либо отказе.
3. **Given** результат или ошибка, **When** выбрано «Очистить», **Then** diff, ошибка и результат исчезают, счётчик равен нулю, фокус возвращается в поле, состояние становится idle.
4. **Given** результат, **When** пользователь меняет diff, **Then** предыдущий результат исчезает и состояние становится idle; результат не выглядит относящимся к изменённому тексту.

### Edge Cases

- Лимит применяется к исходному тексту до удаления секретов; текст не обрезается. Unicode и переносы считаются по предложению A-002.
- Учебный diff содержит неполные hunk-счётчики; UI не требует применимости патча и не исправляет его. Проверка содержательной допустимости принадлежит логике.
- Пустой checks отображается как «Дополнительные проверки не предложены»; отсутствие самого списка — некорректный ответ.
- Удалённая строка может иметь номер из старой версии файла. UI не называет её номером строки новой версии; трактовка подлежит согласованию.
- Длинные пути и доказательства переносятся внутри блока. При ширине 360 CSS-пикселей нет горизонтальной прокрутки всей страницы; локальная прокрутка diff допустима.
- Поздний ответ после завершённого ожидания не заменяет ошибку или результат нового запуска. Двойное нажатие не создаёт параллельных запусков.
- Перезагрузка начинает пустой сеанс. Восстановление формы средствами браузера не считается гарантированным хранением приложением.
- UI не сообщает «PR безопасен» и не обещает выявление всех дефектов либо всех секретов.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: UI MUST предоставлять одну страницу с заголовком, многострочным полем «Diff одного PR», счётчиком «N / 20 000», кнопками «Проверить diff» и «Очистить», областью состояния и результата. Приёмка: US1.1, US3.3.
- **FR-002**: До запуска UI MUST сообщать: анализ ограничен переданным diff; рекомендация не заменяет решение ревьюера; распознаваемые секреты удаляются перед передачей внешней модели, но реальные секреты вставлять не следует. UI MUST не запрашивать ключ модели. Приёмка: проверка текста формы и доступности подсказки с клавиатуры.
- **FR-003**: UI MUST отклонять пустой/пробельный ввод и превышение 20 000 символов, сохраняя текст и сообщая способ исправления; окончательную проверку выполняет логика. Приёмка: US2.1–US2.3.
- **FR-004**: UI MUST иметь четыре взаимоисключающих состояния idle, loading, success, error с поведением из таблицы ниже. Приёмка: US1.1–US1.4, US2.4, US3.3–US3.4.
- **FR-005**: UI MUST разрешать только один активный запуск; во время loading ввод, запуск и очистка недоступны, текст ожидания доступен для чтения. Приёмка: US1.2 и двойное нажатие.
- **FR-006**: UI MUST показывать summary, от нуля до трёх risks и checks без изменения смысла и порядка; каждый риск содержит видимые file, line, evidence и risk. Нулевые списки имеют явные состояния. Приёмка: US1.3–US1.4 и пустой checks.
- **FR-007**: UI MUST показывать безопасные сообщения для недопустимого входа, превышения размера, таймаута, ошибки модели, потери связи и некорректного результата; не показывать внутренний prompt, stack trace или сырой ответ ошибки. Выданный идентификатор запроса доступен для сообщения о проблеме. Приёмка: US2.3–US2.5 и безопасный отказ при неизвестной ошибке.
- **FR-008**: UI MUST сохранять diff при ошибке, завершать loading не позднее 15 секунд с запуска по предложению A-004 и разрешать ручной повтор без автоматических запросов. Поздний ответ завершённого запуска игнорируется. Приёмка: US2.4 и сценарий позднего ответа.
- **FR-009**: UI MUST отображать diff, доказательства и текст модели буквально; не исполнять их и не создавать автоматически активные ссылки из ответа. Приёмка: US1.5.
- **FR-010**: UI MUST очищать предыдущий результат при новом запуске, изменении diff и очистке; очистка также удаляет ввод и ошибки. Приёмка: US1.2, US3.3–US3.4.
- **FR-011**: UI MUST иметь доступные подписи, текстовые ошибки, видимый фокус, логичный порядок клавиатурного перехода, объявляемые статусы и контраст текста не ниже 4.5:1; состояние не передаётся одним цветом. Завершение анализа не перемещает фокус неожиданно. Приёмка: US3.1–US3.2 и проверка контраста.
- **FR-012**: UI MUST поддерживать чтение и действия при ширине от 360 CSS-пикселей и увеличении масштаба до 200%; длинный вывод не перекрывает действия. Приёмка: проверка с длинными путями и evidence.
- **FR-013**: UI MUST не сохранять diff и результат в историю приложения, URL, журналы приложения или постоянное хранилище браузера; допускается текущий экранный сеанс. Допустимый журнал приложения содержит только идентификатор запроса, длительность и статус. Приёмка: проверка перезагрузки, URL, хранилищ и журналов.
- **FR-014**: UI MUST не предлагать approve, merge, изменение кода, запуск checks, выбор модели, загрузку репозитория или анализ файлов вне diff. Checks — рекомендации человеку. Приёмка: обзор всех доступных действий.

#### Экран и состояния

| Состояние | Что видит пользователь | Действия | Переход |
| --- | --- | --- | --- |
| idle | Форма, подсказки и счётчик; результата нет | Редактировать, очистить, запустить | Допустимый запуск → loading; ошибка формы → error |
| loading | Неизменяемый отправленный diff, «Анализируем diff…» | Читать; новые действия анализа недоступны | Корректный ответ → success; отказ/предел ожидания → error |
| success | Форма и три секции рекомендации | Изменить, очистить, запустить снова | Изменение/очистка → idle; запуск → loading |
| error | Сохранённый ввод, причина и способ исправления; результата нет | Изменить, очистить, повторить | Изменение/очистка → idle; допустимый запуск → loading |

### Key Entities *(include if feature involves data)*

- **Diff одного PR**: исходный текст и отображаемая длина; запуск относится к одной зафиксированной версии текста.
- **Рекомендация**: summary — краткое описание; risks — до трёх доказуемых рисков; checks — предложенные проверки.
- **Риск**: file — путь; line — номер строки; evidence — цитата diff или явно названное правило Context Pack; risk — формулировка возможной проблемы. UI отображает доказательства, логика отвечает за их проверку.
- **Ошибка запуска**: категория, безопасное сообщение, при наличии идентификатор запроса; не содержит diff или сырой ответ модели.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: В сквозной демонстрации ревьюер проходит путь «вставить учебный diff → запустить → увидеть три секции результата» без дополнительного ввода; результат содержит 0–3 риска с четырьмя видимыми атрибутами.
- **SC-002**: Во всех проверенных ошибочных сценариях (пустой ввод, 20 001 символ, отказ службы, таймаут, потеря связи, неверная структура) пользователь видит объяснение и сохраняет ввод; максимум ожидания UI — 15 секунд.
- **SC-003**: Все действия основного пути и восстановления доступны с клавиатуры; начало и завершение анализа, ошибки и название поля доступны программе чтения с экрана.
- **SC-004**: При ширине 360 и 1280 CSS-пикселей и масштабе 200% секции и действия читаемы, не перекрываются и не требуют горизонтальной прокрутки всей страницы.
- **SC-005**: Сквозная проверка успеха и хотя бы одной ошибки проводится с UI и логикой вместе. Подмена модели явно отмечается; результат реального вызова не заявляется без такого вызова.

## Assumptions

- **A-001 — предложение UI, не согласовано**: Одна русскоязычная страница для локального учебного сценария; без учётных записей, истории и внешней публикации. Аутентификация публичного сервиса исходниками не определена и находится вне draft.
- **A-002 — предложение UI, не согласовано**: «Символ» — Unicode code point в исходном тексте; пробелы и переносы учитываются, нормализации и обрезки перед подсчётом нет. Это нужно одинаково определить в UI и логике.
- **A-003 — предложение UI, не согласовано**: UI не проверяет полную грамматику unified diff, не применяет patch и не удаляет секреты самостоятельно. Логика проверяет вход, редактирует поддерживаемые секреты и проверяет evidence до выдачи результата.
- **A-004 — предложение UI, не согласовано**: Таймаут LLM остаётся 10 секунд по REL-1; UI прекращает ожидание через 15 секунд, учитывая передачу и обработку. Это само по себе не гарантирует отмену работы службы.
- **A-005 — предложение UI, не согласовано**: Ошибка сохраняет ввод; загрузка блокирует редактирование и очистку; повторы только ручные. Потоковый вывод, отмена, экспорт и автоматическое копирование не входят в первый сценарий.
- **A-006 — зависимость**: Общая версия контракта должна закрепить типы полей, номера строк, категории ошибок и правила распознавания секретов после сопоставления независимых drafts. Предложения команды — в [contract-proposal.md](contract-proposal.md); согласования сейчас нет.
