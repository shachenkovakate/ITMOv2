# AI PR Reviewer Constitution

## Core Principles

### I. Две команды, один контракт

Команды UI и логики MUST подготовить независимые спецификации одной фичи.
Исходные варианты MUST сохраняться; итоговые варианты MUST ссылаться на общий
контракт. Расхождения в данных, вызовах, ошибках и состояниях MUST фиксироваться.

### II. Решение человека до кода

Прикладной код MUST создаваться только после явного согласования спецификаций
и общего контракта пользователем. Подготовка SDD-инструментов и документов
разрешена до этого. Нельзя выдавать рекомендацию агента за решение человека.

### III. Проверяемые рекомендации

Результат ревью MUST содержать summary, до трёх risks и checks согласно
Context Pack из ДЗ 1–2. Для риска MUST быть проверяемая ссылка на diff либо
явно названное правило контекста. Approve, merge и правка PR в продукт не входят.

### IV. Минимизация раскрытия данных

Ключи MUST оставаться вне репозитория и браузерного клиента. Распознаваемые
токены, пароли и приватные ключи MUST заменяться до отправки LLM. Поддерживаемые
форматы и ограничения распознавания MUST быть описаны. В журнале приложения
допустимы только request_id, длительность и статус, без diff и ответа модели.

### V. Проверка пользовательского результата

Приёмка MUST включать работающий UI вместе с логикой: успешный сценарий и
ошибку/границу. Подмена модели допустима для воспроизводимых тестов и MUST
быть обозначена. Реальные вызовы и результаты нельзя имитировать в отчёте.

## Scope and Constraints

Работа выполняется только для ДЗ 5 в ветке practice_05. Источник условия:
../prenetation.pdf, страница 16. Источник продуктового контекста: ../inputs/.
Фреймворк: GitHub Spec Kit, Specify CLI 1.2.3. Требуется сравнение с OpenSpec.
Обязательная граница входа из контекста — 20000 символов; таймаут LLM — 10 секунд.
Новые решения об API, UX и трактовке evidence требуют согласования в контракте.

## Development Workflow

1. Constitution и общий исходный контекст.
2. Независимые drafts UI и логики с предложениями команды и проверкой качества.
3. Сопоставление, общий проект контракта, решение пользователя, обновление обеих спецификаций.
4. Plan, tasks, анализ согласованности; реализация по согласованным артефактам.
5. Сквозные проверки, короткое демо и личная рефлексия пользователя.

## Governance

Эта версия фиксирует требования пользователя, задания и ранее выбранного
проекта. Существенное изменение контракта сначала обсуждается с пользователем,
затем одновременно обновляет обе спецификации и план. Версия меняется по semver.
Документы и проверки не должны утверждать, что этап завершён до фактического
выполнения. Рефлексию студентки записывают только по её собственным сообщениям.
